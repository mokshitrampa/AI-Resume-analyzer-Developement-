Explainable Matching & Scoring Algorithms

Unlike black-box opaque AI systems, this platform implements a transparent, explainable weighted scoring formula computed directly in Java with dynamic weight redistribution.

COMPOSITE JOB MATCH FORMULA:

Final Score = (40% × Required Skills Match)
            + (20% × Preferred Skills Match)
            + (20% × TF-IDF Semantic Cosine Similarity)
            + (10% × Experience Alignment Match)
            + (10% × Education / Degree Match)
⚖️ Dynamic Weight Redistribution (Fairness Guarantee)
If a job vacancy does not specify optional criteria (such as no preferred skills or no minimum years of experience), the engine does not penalize the candidate with 0 points. Instead, it dynamically redistributes unassigned weights proportionally across the active categories so that total active weight always equals 100%.

Deterministic Quality Scoring Rubric (0 to 100):

Quality Dimension Max Points Evaluation Rules
1. Completeness 20 pts Presence of Name, Email, Phone, Education, Skills, and Summary sections (3-4 pts each).
2. Technical Skill Breadth 20 pts Number of verified technical competencies (5+ skills = 10 pts, 10+ = 15 pts, 15+ = 20 pts).
3. Education Information 15 pts Explicit degree title, university name, graduation year, and CGPA/grade.
4. Work Experience 15 pts Presence of engineering internships, roles, company names, and quantified bullets.
5. Applied Projects 15 pts At least two portfolio projects showcasing practical software development.
6. Formatting & Length 10 pts Optimal document length (250 to 1,200 words) conforming to standard 1–2 page hiring conventions.
7. Keyword Relevance 5 pts Industry engineering keywords (e.g. CI/CD, Git, testing, microservices, cloud).

Database Architecture & Entities

The platform utilizes a relational database architecture with strict foreign key constraints, cascading rules, and dual-profile compatibility (MySQL 8 / persistent H2-MySQL):

👥 Core User & Profile Tables

  • users — ID, unique email, BCrypt password, full name, role (STUDENT, RECRUITER, ADMIN), active status.
  • student_profiles — One-to-one link to student user; target job title, degree, CGPA, graduation year.
  • recruiter_profiles — One-to-one link to recruiter user; company name, website, designation.

📄 Resume & Parser Tables

  • resumes — Document metadata, UUID stored filename, file size, content type, upload timestamp.
  • extracted_resume_data — Parsed candidate name, email, raw text, and JSON lists of skills, experience, and education.
  • skills — Technical taxonomy dictionary with canonical name, category, and alias synonyms.

💼 Job & Application Tables

  • jobs — Job title, company name, location, work mode (REMOTE/HYBRID/ONSITE), salary, required and preferred skills.
  • job_applications — Unique composite constraint on (job_id, student_id), match score, status, cover letter, recruiter notes.
  • saved_jobs — Bookmark table for students to save vacancies for later.

📊 Scoring & Analysis Tables

  • resume_analyses — Historical record of 0–100 quality scores, category subscores, strengths, weaknesses, and improvement tips.
  • job_match_results — Historical record of calculated match scores, component breakdown, matching skills, and formula explanations.

University Viva Voce & Lab Presentation Q&A

Q1: Why did you implement TF-IDF and Cosine Similarity in pure Java instead of using Python?

Answer: Implementing the text processing, vectorization, and cosine math directly in Java eliminates the need for an external Python subprocess or microservice. This guarantees zero network latency between services, eliminates cross-language serialization overhead, avoids external server dependencies, and ensures the entire application runs natively on the JVM using standard Java collections.

Q2: How does the system handle resumes with different skill aliases (e.g., "JS" vs "JavaScript")?

Answer: The platform maintains a canonical skill taxonomy in the SkillExtractionService containing over 150 technical competencies. Each skill possesses an array of known aliases and synonyms. The tokenization engine uses boundary-aware regex matching to detect aliases in the extracted text stream and automatically normalizes them to their canonical name. Substring false-positives (such as matching "Java" inside "JavaScript") are prevented using word-boundary assertions.

Q3: What happens if a job description doesn't specify preferred skills or required experience?

Answer: The system applies dynamic weight redistribution. Instead of awarding 0 points or penalizing the student, the calculator identifies only the active criteria and redistributes the unassigned weights proportionally across the remaining categories so that total active weight still sums to 100%.

Q4: How does the application ensure data privacy and prevent unauthorized resume access?

Answer: Resumes are stored on disk using randomized UUID filenames outside the web context root, preventing direct URL access. File endpoints are protected by Spring Security 6 with stateless JWT tokens. A student can only access their own uploaded resumes. Recruiters cannot access a student's resume document unless the candidate explicitly submits an application to that recruiter's job opening.
